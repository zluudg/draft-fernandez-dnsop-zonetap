2.  Conventions and Definitions

   The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT",
   "SHOULD", "SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED", "MAY", and
   "OPTIONAL" in this document are to be interpreted as described in
   BCP 14 [RFC2119] [RFC8174] when, and only when, they appear in all
   capitals, as shown here.

   Zone Transparency Service: A service that provides information about
   a zone such as what records have been added and deleted, if the zone
   has been transferred to a new registrar or if the registrant has
   changed.

   Discoverer: Someone trying to discover a zone transparency service.
   This could be either a human that performing some kind of forensic
   investigation or troubleshooting a network issue or an automatic
   program that is looking for a connection point.

3.  The ZONETAP Resource Record

   The ZONETAP RR is used to signal the availability of a zone
   transparency service, how to connect to it and how to interpret the
   data it serves.  It MUST exist at the apex of a zone so a particular
   zone's transparency service can be easily discovered by interested
   parties.

   The RR Type code for the ZONETAP RR is TBD.

3.1.  The ZONETAP RDATA Format

   The RDATA of the ZONETAP presentation format consists of two text
   that guides the discoverer to where it can find a zone transparency
   service and what kind of content it can expect.

3.1.1.  The SERVICE-ID Field

   The SERVICE-ID field consists of a URI (TODO-ref) that tells the
   discoverer where and how to fetch the zone data.  This draft supports
   the following schemes:

             +========+=====================================+
             | Scheme | Description                         |
             +========+=====================================+
             | dns    | Zone transparency service available |
             |        | via an open zone transfer [RFC4501] |
             +--------+-------------------------------------+
             | http   | Zone transparency service available |
             |        | via HTTPS TODO-ref                  |
             +--------+-------------------------------------+
             | https  | Zone transparency service available |
             |        | via HTTPS TODO-ref                  |
             +--------+-------------------------------------+

                                 Table 1

   For SERVICE-ID field URIs with a "dns" scheme, the "dnstypeval"
   parameter SHOULD have a value of AXFR or IXFR (or their corresponding
   numerical values) to indicate that the zone is available via an open
   zone transfer at the given "dnsauthority".  Standard ports are
   assumed if not explicitly part of the "dnsauthority".  I.e. tcp port
   853.  The "dnsclassval" SHOULD be "IN", the Internet class, or
   omitted, which is equivalent.

   For SERVICE-ID field URIs with a "http" or "https" scheme, field
   SHOULD contain a URL from where the zone data can be fetched.

   Furthermore, the SERVICE-ID field can be set to a period (hex value
   0x2E), to explicitly state that there is no zone transparency service
   available for the zone in question.

3.1.2.  The FORMAT Field

   The FORMAT field shows how the DNS transparency information that is
   being shared is represented and its allowed values vary depending on
   the scheme in the SERVICE-ID field.  For records with a "dns" scheme,
   the model field MUST have one of the following values:

    +=======+==========+=============================================+
    | Value | MNEMONIC | Description                                 |
    +=======+==========+=============================================+
    | 1     | SIGNED   | A signed version of the zone is provided    |
    +-------+----------+---------------------------------------------+
    | 2     | UNSIGNED | An unsigned version of the zone is provided |
    +-------+----------+---------------------------------------------+

                                 Table 2

   For records with a "http" or "https" field, the FORMAT field SHOULD
   be a valid MIME type (TODO-ref).  For example, it could be set to
   "text/plain" for a transparency service that publishes zone data as a
   text file.  A discoverer MAY try to interpret values that are not
   valid MIME types.  For example, if the value is a URL that points to
   a JSON schema (TODO-ref), the discoverer can try to use that as its
   data model.

   For a record with a SERVICE-ID field set to a single period to
   indicate the non-existance of a zone transparency service, the FORMAT
   value can be set to anything and discoverers SHOULD ignore it since
   it adds no meaningful information to the fact that there is no zone
   transparency service.

3.2.  The ZONETAP Presentation Format

   For a service that exposes the signed zone data and supports
   incremental zone transfers, the record would look like:

   example.  86400 IN ZONETAP dns:zonetap.example.?TYPE=IXFR SIGNED

   For a service that exposes an unsigned version of the zone on a non-
   standard portand only supports AXFR, the record would be:

   example.  86400 IN ZONETAP dns:zonetap2.example.:20000?TYPE=AXFR
   UNSIGNED

   A service that consists of publishing a text file with a list of the
   zone contents (i.e. a zone file as it often appears on disk), the
   record would be:

   example.  86400 IN ZONETAP https://zonetap3.example/example.zone
   text/plain

   A service that encodes the zone content and enriches it with, for
   instance, WHOIS data according to a specific data model would look
   like:

   example.  86400 IN ZONETAP https://zonetap4.example/example.json
   https://schemas.example/zone-transparency.json

4.  Security Considerations

   A zone transparency service SHOULD try to provide the data in an
   authenticated manner.  For services using the "https" scheme, relying
   on WebPKI (TODO-ref) is most likely sufficient.  Services using the
   "dns" scheme, can publish a TLSA TLSA record [RFC6698].  For
   instance, the service:

   example.  86400 IN ZONETAP dns:zonetap5.example.?TYPE=AXFR UNSIGNED

   Would publish the following TLSA record:

   _853._tcp.zonetap.example.  IN TLSA 3 0 0
   30820307308201efa003020102020...
